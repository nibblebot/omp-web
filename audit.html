Executive summary

omp-web is a well-documented, test-covered (293 passing tests) Bun + Solid.js product with a clear architectural story — a single-session daemon (omp-session) fronted by a multi-session supervisor (omp-fleet) sharing one wire contract. The audit confirms the design is fundamentally sound, but found one critical security flaw (shell injection through fleet spawn-template substitution), a class of stream-lifecycle bugs that can permanently wedge or detach sessions (backpressure kill indistinguishable from dormant close, >4 MiB history priming, double-applied SSE resume deltas, no edge-pipe resume, double-launch on concurrent respawn), and a collab double-broadcast bug. On the product side, the README over-promises (collab UI, method counts, sidebar claims), the quickstart omits the model-provider prerequisite, and the strategic audit finds the headline "web UI for a CLI agent" position largely absorbed by incumbents — the defensible moat is the ops/security model (single binary, in-process SDK, dial-in-only sandboxes, disposable daemons), which the current positioning under-sells.

  • Fix first: spawn-template shell injection (#19), collab double-broadcast (#10), >4 MiB priming lockout (#11), respawn double-launch (#20), AskDialog keyboard trap (#32).
  • Then: the SSE/stream lifecycle cluster (findings #0–#4) — several independently reported bugs share root causes in resume/reconnect handling.
  • Strategic: reposition around the ops moat (#72), ship fan-out in the roster UI (#73), package omp-fleet as a binary (#75), and reconcile README with reality (#64–#67).

Baseline at audit time: bun test → 293 pass / 25 fail / 10 errors (fleet integration failures); bun run check:types fails — tsgo not installed (bun install needed). Remediation plan: audit-plan.md. Method: 10 parallel specialist auditors; every critical/high/medium finding was adversarially verified against source by independent refuters (34 verified; low/info findings are reported as-found).

MEDIUM#0

Daemon backpressure stream-kill is indistinguishable from dormant close — connector marks live daemon "asleep", next wake kills it

verified ×1
Evidence

Daemon side: server/index.ts:246-253 — enqueueTo() calls terminateStream(stream,"backpressure") past SSE_BACKPRESSURE_BYTES; terminateStream (server/index.ts:262-269) ends the response with stream.controller.close(), i.e. a clean EOF on the wire. Connector side: fleet/connector.ts #consume() finishes its parseSseUnits loop without error and calls #onStreamEnded(state,{clean:true}), whose clean branch transitions the daemon to "asleep" ("Clean end: the daemon went dormant"). Nothing distinguishes a backpressure kill from a dormant exit. Consequence: for a spawned daemon the supervisor child is still alive (#children entry intact — supervisor's clean-exit→asleep guard at fleet/supervisor.ts:445 requires exitCode===0, which never happened), yet the registry says asleep. When the user then attaches or clicks spawn_resume, FleetEdge.#wake (fleet/edge.ts:697-718) takes the entry.mode==="spawned" && status==="asleep" branch → SpawnSupervisor.respawn (fleet/supervisor.ts:194-216), which SIGTERMs the still-running child with only RESP_AWN_KILL_GRACE_MS=2s grace and replaces it with --resume — killing an in-flight turn that the drop-and-resume design (server comment: "the client resumes via Last-Event-ID") explicitly intended to survive. Remote daemons hit the same mislabel (alive but shown asleep).

Recommendation

Make backpressure termination distinguishable from a dormant close: use controller.error() instead of controller.close() for the backpressure path (the connector's catch already maps non-clean ends to "reconnecting" + jittered redial with Last-Event-ID, which is exactly the intended drop-and-resume), or send a terminal reason frame before closing that the connector checks before choosing "asleep".

Verification notes
  • Finding verified end-to-end against source. Daemon: enqueueTo (server/index.ts:247-253) terminates past SSE_BACKPRESSURE_BYTES (4MiB, src/protocol.ts:169) via terminateStream (server/index.ts:261-269) which uses controller.close() — clean EOF, no error(), no reason frame; its own comment expects the client to resume via Last-Event-ID. Connector: #consume (fleet/connector.ts) completes its parseSseUnits loop without error on such an EOF (parseSseUnits only throws on reader error, src/sse.ts) and #onStreamEnded's clean branch transitions to "asleep" with no redial; only a thrown read error maps to "reconnecting" + Last-Event-ID redial. Supervisor: the clean-exit→asleep guard (fleet/supervisor.ts:444-447) requires exitCode===0 && signalCode===null, so a still-alive child never reconciles the mislabel; respawn (fleet/supervisor.ts:190-216) SIGTERMs the live child with RESP_AWN_KILL_GRACE_MS=2s then relaunches --resume. Edge: #wake (fleet/edge.ts:697-718) routes mode==="spawned" && status==="asleep" to supervisor.respawn for both attach and spawn_resume. Reachability is real, not theoretical: a single block > 4MiB (large call_result, e.g. big file read) kills every stream including the fast-reading connector's, and for an unattached spawned daemon the connector is the only stream; the daemon stays alive (in-flight bash/python suppress idle-exit, server/index.ts:149-151). Consequence follows: live daemon shown asleep, next wake kills a working child and the in-flight turn; --resume only restores the last persisted session. Recommendation is sound: controller.error() on the backpressure path drives the connector's existing clean:false → reconnecting → Last-Event-ID redial path (both branches are distinct and test-covered in connector.test.ts), which is exactly the drop-and-resume the daemon comment intends. No existing mechanism distinguishes or auto-corrects the mislabel.
MEDIUM#1

Connector idle-drop never arms without a retain/release pair — never-attached fleet daemons stay awake forever

verified ×1
Evidence

fleet/connector.ts: release() is the ONLY place state.idleTimer is armed ("if (state.retainCount === 0 && state.idleTimer === null) state.idleTimer = setTimeout(... disconnect ...)"); connect() clears but never arms it. A daemon dialed without any retain — spawned daemons dialed by the supervisor at endpoint resolution (fleet/supervisor.ts:411), remote entries dialed by /ctl/add or /ctl/provision (fleet/server.ts:427,462) — holds its control socket open forever. The connector test codifies this: fleet/fanout.test.ts:338 comment "Arm the idle policy (drop happens only after a retain/release pair)". Daemon side, the open socket permanently defeats R11: isIdleSuppressed() (server/index.ts:2273-2274) returns true whenever streams.size > 0, and idleCheckTick() calls markActivity() while suppressed, so the 30m default idle auto-exit (server/config.ts: parseDuration(... ?? "30m")) never fires. README.md:75 promises "with no attached clients … omp-session shuts down cleanly after the idle timeout — … omp-fleet marks the entry asleep and respawns it on demand" — that only happens for daemons a browser (or fan-out prompt) attached to at least once.

Recommendation

Arm the idle-drop timer when a connection reaches "ready" with retainCount===0 (or on connect), not only in release(), so unused control sockets drop and the daemon's own idle timer can fire — matching the connector's documented idle policy ("subscribers drop to zero … letting the daemon's own idle timer fire").

MEDIUM#2

SSE resume double-applies deltas: fresh history priming + ring replay duplicates chat items and strands tool cards

verified ×1
Evidence

server/index.ts:1688-1720 primeConsumer() ALWAYS writes the full priming (attached → history → state …) and then, when Last-Event-ID ≥ SSE_DELTA_SEQ_START, replays ring.after(last). The replayed ring includes "event" deltas (RING_DELTAS.event, server/index.ts:225) whose transcript effects are already inside the just-primed history. Client side (src/state.ts): the "history" case calls loadHistory() (state.ts:678) which rebuilds state.items from the transcript; the replayed events then go through applyEvent(), where message_start pushes a user item, message_end pushes an assistant item, and tool_execution_start pushes a tool item — all unconditionally, no identity dedup (state.ts:492-556). Worse, the replayed tool_execution_end uses findToolIndex (first match, state.ts:582-598), which resolves the history-built card, leaving the replayed duplicate tool card stuck in "running" forever. Trigger: native EventSource auto-reconnect (the only path that sends Last-Event-ID — manual reconnects create a fresh EventSource without one) while the agent completes a message/tool during the drop — precisely the case SSE resume exists for. In roster mode the damage self-heals (edge priming is roster-only; the re-attach pipe priming delivers a fresh history afterward), so this bites the standalone daemon UI. SSE-plan.md:78 documents priming+replay as designed but never addresses the overlap.

Recommendation

Make replay non-overlapping with the snapshot: capture nextDeltaSeq S when priming is built and replay only ring entries with seq > max(lastEventId, S-1) (deltas ≤ S are fully reflected in the fresh history/state), or drop event/tool deltas client-side that predate the priming history. At minimum, dedupe pushed items by message/toolCallId and make tool_execution_end resolve the newest matching running card.

(1) server/index.ts primeConsumer (1690-1724) always enqueues the full priming — including {type:'history', messages: entry.session.messages} at line 1709 — then at 1720-1723 replays ring.after(last) whenever last >= SSE_DELTA_SEQ_START (1024, src/protocol.ts:167). (2) RING_DELTAS.event=true (line 224) and session.subscribe (1032-1033) → broadcastTo (296-302) ring every AgentSessionEvent, so message_start/message_end/tool_execution_start/end for turns completed during a drop sit in the replay window AND their messages are in the primed history — overlap is real, not speculative. Severity medium is fair: user-visible duplicate chat items plus a permanently 'running' tool card on any transient network blip mid-turn. Recommendation (skip replay ≤ snapshot seq, or client-side dedup/newest-match) targets the actual defect.
MEDIUM#3

Fleet restart leaves stale registry statuses — no boot-time reconciliation or redial

verified ×1
Evidence

Registry.load() (fleet/registry.ts:51-71) restores entries with their persisted statuses verbatim, and startFleet/FleetServerImpl (fleet/server.ts:522-526, constructor ~269-301) only runs supervisor.backfillWorktrees() and startGitStatePolling() — nothing re-dials, resets, or expires statuses. After a fleet restart: (a) entries persisted "ready" are displayed ready with uptime computed from the stale readyAt (toRosterEntry, fleet/edge.ts:285), though their children/sockets died with the old process — they self-heal only when a user attach triggers a dial → onDialFailed → respawn; (b) entries persisted "spawning" are stuck forever: the endpoint-resolution timer (fleet/supervisor.ts:392-397) lived in the dead process, spawn_resume rejects them ("not asleep", fleet/edge.ts:619-623), and only a manual stop() (which unconditionally sets asleep, fleet/supervisor.ts:239-241) unsticks them; (c) "reconnecting"/"resolving" similarly persist as lies. The registry is the roster's source of truth, so the fleet's primary UI is wrong after every restart until manual interaction.

Recommendation

Reconcile at load/boot: map non-terminal persisted statuses to a truthful boot state (spawned+no live child → "asleep" since respawn --resume is the documented recovery; remote → "connecting" + immediate connector.connect, or "asleep"), and treat "spawning" entries as failed spawns (error or asleep).

MEDIUM#4

Edge proxy pipe has no resume — one dropped daemon stream permanently detaches the browser

verified ×1
Evidence

fleet/edge.ts: #openPipe (726-762) dials the daemon's /events once per attach with no Last-Event-ID and no redial logic; #consumePipe (764-783) treats any end — error OR clean EOF — as terminal and calls #pipeLost (795-802), which releases the retain and emits a single "daemon connection lost" error frame. The client (src/state.ts:1521-1534) just sets state.error; the tab stays attached to nothing until the user re-clicks the daemon (the onopen re-attach at state.ts:1300 doesn't fire — the browser's own stream never closed). Contrast: the connector redials with Last-Event-ID (fleet/connector.ts:354-357), and browsers auto-resume via EventSource — the pipe is the only consumer that ignores the daemon's drop-and-resume contract (server/index.ts:261 "the client resumes via Last-Event-ID"). One daemon-side backpressure trip on the pipe (or a transient network flap to a remote sandbox) permanently detaches the browser from a healthy daemon.

Recommendation

Give the pipe the same resume semantics as the connector: on non-intentional pipe end, redial /events with Last-Event-ID (pipe tracks the last forwarded daemon seq) with bounded backoff, instead of declaring the connection lost after a single failure.

LOW#5

Edge rings full-history and large answer frames the daemon deliberately never rings — per-client memory unbounded in bytes

reported
Evidence

fleet/edge.ts #onPipeFrame (790-815) forwards every daemon frame via #sendDelta, which unconditionally pushes into the per-client SseRing (cap SSE_RING_CAP=10_000 ENTRIES, src/sse.ts SseRing). The daemon deliberately does NOT ring these (RING_DELTAS, server/index.ts:218-235, excludes history/available_commands/call_result: "Priming frames and unicast answers are NOT ringed"). The edge rings them anyway: every session replacement broadcasts a full-transcript history frame (broadcastHistory, server/index.ts:890-892) and large call_result payloads (formatSessionAsText, getSubagentMessages transcripts, exportHtml) land in every attached browser client's ring. With multi-MB transcripts, one client × 10k entries × MB-scale frames is an unbounded memory ceiling per browser at the edge; on resume the stale history is also replayed pointlessly (the re-attach priming immediately re-sends a fresh one).

Recommendation

Mirror the daemon's RING_DELTAS filter at the edge (ring only delta types; history/available_commands/call_result are re-derivable via re-attach/re-POST), and/or make SseRing byte-bounded rather than entry-bounded.

INFO#8

Per-browser pipe fan-out: N+1 daemon streams and unicast answers broadcast to every browser pipe

reported
Evidence

Each browser attach opens a dedicated daemon /events stream (PipeState, fleet/edge.ts:236-248, #openPipe:726-762) ON TOP of the connector's per-daemon control socket, so N browsers viewing one daemon = N+1 SSE streams; the daemon's broadcast/broadcastTo (server/index.ts:271-294) enqueues every frame to every stream. Unicast answers are also fanned out to all: broadcastAnswer (server/index.ts:281-285) sends call_result/login_url/etc. to every live stream — browser A's call_result travels the fleet↔daemon link on browser B's pipe and the control socket, and is delivered to B's browser (client ignores unknown ids, src/state.ts:1376). For remote sandboxes over ssh -L/tailnet this multiplies bandwidth per attached browser; large answers (transcripts, exports) are the expensive case. Single-operator assumption (README non-goals) caps the blast radius, hence info.

Recommendation

Acceptable today; if multi-browser matters, multiplex browsers over the connector's single control socket (it already fans frames to listeners) and address unicast answers by command id instead of broadcast.
