omp-web: SDK-based WebSocket protocol vs. omp RPC

The agent runs in-process via the @oh-my-pi/pi-coding-agent@17.1.8 SDK (createAgentSession) inside a Bun daemon. The browser never speaks JSON-RPC — src/protocol.ts owns a typed WebSocket frame protocol layered on the SDK. This page is the architecture + capability reference: what the WS protocol does, what RPC mode was, and where one beats the other.

● now — SDK + WebSocket protocol ● replaced — RPC mode (baseline) ● shared — SDK / agent runtime ● collab — TUI guests
01 · Current architecture

SDK in-process · WebSocket bridge · multiplexed sessions

One Bun process hosts N agent sessions created with createAgentSession. Each socket attaches to exactly one session handle; session-scoped frames broadcast to every tab attached to that session, so multi-tab consistency is free. Collab rooms (/r/:roomId) let real omp TUI clients join a web-hosted session.

Routing is by socket attachment: call/login_code/ui_response target the attached session; event/state/history/bash_chunk are session-scoped broadcasts; live_sessions/daemons/process_stats are global.
Wire is ours, not RPC's src/protocol.ts owns every frame. RPC wire types survive only as local, structurally-verbatim type copies for client compatibility. New capability = one WebMethodName union member + one dispatch row.
Sessions outlive sockets Closing a tab detaches; the session keeps running. close_session → beginDispose() + dispose(). Per-session private AgentRegistry/EventBus/SessionManager.
Collab inverts the TUI relationship The web daemon is the collab host; real omp TUIs join rooms. Guests prompt/steer/abort, answer dialogs (web falls through when no writable guest), and see the live transcript/roster.
Prompt is fire-and-forget session.prompt() resolves at turn end, so the server never awaits it — call_result returns immediately and events stream in as they happen.
02 · What it replaced

RPC mode: agent as a child process over stdio

Before the SDK conversion (2026-08-05), the server spawned the agent binary and spoke JSON-RPC-ish frames over stdin/stdout: 1 process = 1 agent, point-to-point, with two hard ceilings the pinned 17.1.8 client shipped — slash-command output frames were dropped (C1) and extension_ui_request was never forwarded (C2).

The SDK's RPC mode still exists in the package for other embedders; omp-web no longer uses it (grep modes/rpc src/ server/ → nothing). Its dispatch table was the exact specification for the new in-process METHODS adapter.
03 · On the wire

One turn through the WS protocol

The frames the browser actually sees: typed ClientCommand unions up, ServerFrame unions down — session-scoped, unicast, or global. 

sequenceDiagram
  autonumber
  participant T as Browser tab
  participant W as WS hub
  participant D as Dispatch (server)
  participant A as SDK session
  T->>W: call { id, method:"prompt", args }
  W->>D: route via attached session handle
  D->>A: session.prompt(text) — fire-and-forget
  D-->>T: call_result { ok:true } — immediate
  loop Turn runs
    A-->>D: AgentSessionEvent (message_start/update/end · tool_* · agent_end)
    D-->>T: event frame → session-scoped broadcast (every tab on s1)
  end
  D-->>T: state frame on agent_end (with usage stats)
  T->>W: call { method:"bash", args:[cmd] }
  D->>A: session.executeBash(cmd, onChunk)
  loop while streaming
    A-->>D: onChunk(text)
    D-->>T: bash_chunk { id, text } — live
  end
  D-->>T: call_result { ok:true, data: BashResult }
  Note over A,D: ask tool fires an ExtensionUIContext dialog
  A-->>D: ui_request (askDialog)
  D-->>T: ui_request frame (or collab guest answers first)
  T-->>D: ui_response { result }
  D-->>A: dialog resolves → answer lands in the turn
The RPC-mode analogues that exist (prompt, bash, extension UI) delivered no streaming chunks and no dialog round-trip on 17.1.8 — the WS layer adds both as frames.

05 · Bottom line

More powerful where it counts — with two honest trade-offs

WS protocol wins

  • Multiplexing — N sessions per process; tabs attach/detach; sessions outlive sockets.
  • Subagent control — steer/abort individual agents; RPC was observe-only.
  • Real dialogs — ui_request round-trip fixes the C2 ceiling; collab guests answer first.
  • Live streaming — bash/python/btw chunks broadcast session-scoped, abortable.
  • Collab hosting — real TUIs join web-hosted sessions via omp join.
  • Multi-tab consistency — session-scoped broadcast replaces a private 1:1 pipe.
  • Ops surface — live roster, process stats, daemon logs/stop/restart, settings schema, /download.

RPC-only / watch items

  • Host-tool & host-URI bridge — RPC lets the host implement tools; the WS server exposes a fixed allowlist instead.
  • Crash containment — RPC isolated agent failures in a child process; in-process SDK failure takes the daemon down.
  • Cursor-paged history — RPC had get_messages_page; the web protocol ships full transcripts.
  • Attack surface — unauthenticated LAN listener; guard with firewall/SSH tunnel (OMP_WEB_COLLAB_URL exists for remote relay).
  • Single auth identity — all sessions share one authStorage/ModelRegistry pair (SDK-enforced).
