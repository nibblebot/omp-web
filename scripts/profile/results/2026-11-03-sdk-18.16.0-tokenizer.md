# 2026-11-03: SDK 18.16.0, history attach and the fake model's tokenizer

Transport profile check for the `maint/sdk-18.16.0` branch: the SDK bump from 18.15.0 to 18.16.0 plus four features that add call shapes to `lib/wire/protocol.ts` (`resumeList` `phase`, `predictNextMessage` `choices`, `btwInject`; the bash minimizer note is web only).

## Method

- **Harness:** `bun run profile`, 5 reps x 20 s per scenario, 1 warmup, default pinning, isolated fleet with real session processes and the fake model.
- **Arms:** `main` at `b4b02c23` (SDK 18.15.0), the SDK bump alone at `87016421`, and the branch head with the four features.
- **Raw data:** local and gitignored, under `.profile-out/` of the worktrees used for the run. They are only comparable on this host and pinning.

## Result

Against plain `main`, history attach looked about 3 times slower and session CPU rose with it:

| Scenario | Metric | main | branch |
|---|---|---|---|
| s1-history | attach.history.ms | 5.86 | 17.3 |
| s1-history | attach.ttff.ms | 3.09 | 14.1 |
| s1-history-large | attach.completed.ttff.ms | 17.5 | 94.5 |
| s1-history-large | cpu.sessions.ms | 890 | 3400 |

The bump commit alone (`87016421`) gives the same numbers, so the four features add nothing measurable.

**Cause:** the profile's fake model (`profilefake/profile-1` in `scripts/profile/fake-model/config.ts`) declares no tokenizer family. Up to 18.15.0 the SDK estimated context for such a model with a bytes/4 guess, unless `PI_TOKENIZER_ACCURATE=1` was set. 18.16.0 removed that variable and counts every model natively, in o200k_base when the family is unknown (pi-agent-core changelog, #17607). Every `state` frame carries `getContextUsage()`, so priming a large history now pays a native count of it. Claude and GPT models already had a known family, and so were already counted natively on 18.15.0.

**Check:** `main` run with `PI_TOKENIZER_ACCURATE=1` (native counting, like 18.16.0) against the branch. s1-history and s1-history-large attach, priming, reattach and session CPU were all within noise, and so were s3-tools and combined session CPU and command RTT. One metric stayed flagged, s3-tools `stream.latency.p95` at +0.33 ms (0.91 to 1.23 ms, noise band 0.23 ms), sub-millisecond and from one run. Peak RSS was flagged in the first run (s1 session +70 MiB, fleet +16 to 24 MiB) but did not recur in the second.

**Consequence for later runs:** a baseline recorded on 18.15.0 or older is not comparable on history attach with one on 18.16.0 or newer. Record both arms on the same side of this bump, or run the older arm with `PI_TOKENIZER_ACCURATE=1`. Users on models with a known tokenizer family see no change; users on Gemini, Grok or a custom model without a declared tokenizer pay the same counting cost Claude users already paid.
