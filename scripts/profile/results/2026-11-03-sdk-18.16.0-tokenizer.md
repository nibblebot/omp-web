# 2026-11-03: SDK 18.16.0, history attach and the fake model's tokenizer

Transport profile check for the `maint/sdk-18.16.0` branch: the SDK bump from 18.15.0 to 18.16.0 plus four features that add call shapes to `lib/wire/protocol.ts` (`resumeList` `phase`, `predictNextMessage` `choices`, `btwInject`; the bash minimizer note is web only).

## Method

- **Harness:** `bun run profile`, 5 reps x 20 s per scenario, 1 warmup, default pinning, isolated fleet with real session processes and the fake model.
- **Arms:** `main` at `b4b02c23` (SDK 18.15.0), the SDK bump alone at `87016421`, and the branch head with the four features.
- **Raw data:** local and gitignored, under `.profile-out/` of the worktrees used for the run. They are only comparable on this host and pinning.

## Result

Against plain `main`, history attach looked about 3 times slower and session CPU rose with it:

| Scenario | Metric | main | branch |
|---|---|---|---|
| s1-history | attach.history.ms | 5.86 | 17.3 |
| s1-history | attach.ttff.ms | 3.09 | 14.1 |
| s1-history-large | attach.completed.ttff.ms | 17.5 | 94.5 |
| s1-history-large | cpu.sessions.ms | 890 | 3400 |

The bump commit alone (`87016421`) gives the same numbers, so the four features add nothing measurable.

**Cause:** the profile's fake model (`profilefake/profile-1` in `scripts/profile/fake-model/config.ts`) declares no tokenizer family. Up to 18.15.0 the SDK estimated context for such a model with a bytes/4 guess, unless `PI_TOKENIZER_ACCURATE=1` was set. 18.16.0 removed that variable and counts every model natively, in o200k_base when the family is unknown (pi-agent-core changelog, #17607). Every `state` frame carries `getContextUsage()`, so priming a large history now pays a native count of it. Claude and GPT models already had a known family, and so were already counted natively on 18.15.0.

**Check:** `main` run with `PI_TOKENIZER_ACCURATE=1` (native counting, like 18.16.0) against the branch. s1-history and s1-history-large attach, priming, reattach and session CPU were all within noise, and so were s3-tools and combined session CPU and command RTT. One metric stayed flagged, s3-tools `stream.latency.p95` at +0.33 ms (0.91 to 1.23 ms, noise band 0.23 ms), sub-millisecond and from one run. Peak RSS was flagged in the first run (s1 session +70 MiB, fleet +16 to 24 MiB) but did not recur in the second.

**Consequence for later runs:** a baseline recorded on 18.15.0 or older is not comparable on history attach with one on 18.16.0 or newer. Record both arms on the same side of this bump, or run the older arm with `PI_TOKENIZER_ACCURATE=1`. Users on models with a known tokenizer family see no change; users on Gemini, Grok or a custom model without a declared tokenizer pay the same counting cost Claude users already paid.

## Follow-up: where the cost goes, and the fix

**What the SDK does.** `getContextUsage()` (`session/session-stats.ts`, `getContextBreakdown`) takes the newest assistant turn's provider-reported usage as an anchor and counts only the messages after it. With no anchor it counts every message in the active context. The tokenizer memoizes a count per message identity, but only for messages that are settled: `isEstimateCacheable` (`pi-agent-core` `compaction/message-cache.ts`) refuses an assistant turn whose `usage.totalTokens` is 0 or whose stop reason is `aborted` or `error`, and a turn like that is not an anchor either. The fixture in `scripts/profile/fixture.ts` writes every assistant turn with all-zero usage, so each call recounts all the assistant text and tool-call arguments natively, every time. User and tool-result messages hit the identity cache after the first call.

**Measured** (throwaway in-process script: the fixture's session file resumed through `createAgentSession` with the profile agent directory, then timing the calls on this host):

| History | Usage on assistant turns | 1st call | repeat calls | `getSessionStats()` |
|---|---|---|---|---|
| s1-history shape (1200 messages) | zero (the fixture) | 40.6 ms | 5.6 to 5.9 ms | 5.7 to 6.1 ms |
| s1-history shape | recorded (20 tokens) | 14.3 ms | 0.01 to 0.03 ms | 0.07 to 0.40 ms |
| s1-history-large shape (8000 messages) | zero (the fixture) | 169 ms | 35 to 40 ms | 35 to 37 ms |
| s1-history-large shape | recorded | 14.7 ms | 0.03 to 0.08 ms | 0.38 to 0.79 ms |

So the cost is not once per process and not once per attach: with unrecorded usage every call pays it in full (about 5.7 ms and 36 ms), and the first call also warms the fragment cache and the native tokenizer (a one-off 14 ms even when anchored). With recorded usage, which is what a session that ran against a real provider has, the call is anchored and costs microseconds after that first call. The profile's history shape is therefore the worst case: a resumed session with no usage, or a provider that reports none. The fixture is left as is, so the saved baselines stay comparable.

**Redundant calls in omp-web.** The attach priming (`primingFrames` in `apps/session/index.ts`) built the `state` frame with `session.getContextUsage()` and then called `session.getSessionStats()` for the same frame, and `getSessionStats()` computes `contextUsage` again. That is two full counts per attach, which matches the regression: attach `ttff` grew by 11 ms (3.09 to 14.1) on the 300-round history, about 2 x 5.7 ms, and by 77 ms (17.5 to 94.5) on the 2000-round one, about 2 x 36 ms. The post-turn `state` frame (`broadcastState(entry, true)`) and the fleet-pair `state` publish read both the same way. A state frame without stats (`queue_update`, rename, config changes, method follow-ups) makes one call, and collab builds its state under a debounce, once per change and only in a room; those are one count each and are left alone.

**Fix.** `buildStateSnapshot(entry, stats?)` takes the stats the caller already read and uses their `contextUsage`; the priming, the post-turn broadcast and the pair publish read the stats once and pass them. The figure is read at the same synchronous moment as before, so it is never staler than the frame. No cache sits across calls: the SDK exposes no revision for message or model changes (`contextUsageRevision` only tracks the in-flight snapshot), and an omp-web memo keyed on message count and model would miss in-place rewrites (prune, shake) and streaming mutation, so a second count per attach is not worth a stale figure risk. The one count that remains is inherent to the SDK for a history without recorded usage.

**Re-measured**, `bun run profile --scenario s1-history,s1-history-large`, 5 reps, same host and pinning, against `main-accurate` (18.15.0 `main` with native counting, which also reads the context twice per attach) and `main-b4b02c23` (18.15.0 `main`, bytes/4):

| Scenario | Metric | main-b4b02c23 | main-accurate | before fix (18.16.0) | after fix | vs main-accurate |
|---|---|---|---|---|---|---|
| s1-history | attach.ttff.ms | 3.09 | 14.06 | 14.1 | 8.67 | -38% |
| s1-history | attach.history.ms | 5.86 | 17.48 | 17.3 | 11.83 | -32% |
| s1-history | attach.primed.ms | 6.09 | 17.78 | n/a | 12.15 | -32% |
| s1-history | reconnect.reattach-primed.ms | 7.12 | 18.16 | n/a | 12.52 | -31% |
| s1-history | cpu.sessions.ms per 1k h1 frames | 292 | 1007 | n/a | 651 | -35% |
| s1-history-large | attach.completed.ttff.ms | 17.46 | 93.24 | 94.5 | 55.18 | -41% |
| s1-history-large | attach.completed.primed.ms | 35.51 | 117.7 | n/a | 74.79 | -36% |
| s1-history-large | cpu.sessions.ms | 890 | 3430 | 3400 | 2100 | -39% |

The `main-b4b02c23` column is still ahead by one count (about 5.6 ms and 36 ms): that is the SDK's native count of a history with no recorded usage, against the bytes/4 guess it replaced. Totals for s1-history (`cpu.*.ms`, `h1.frames`) are not comparable across runs because a faster attach fits more attaches into the 5 s window (`h1.frames` +46%); the per-frame rows above are. Fleet CPU per frame is within noise (178 vs 179 ms per 1k frames), as it should be: the fix is session-side. s1-history-large `rss.*.peak` flagged against `main-accurate` (fleet +28 MiB, session +212 MiB, noise band 24 and 204 MiB), a single run with a band as wide as the delta.
